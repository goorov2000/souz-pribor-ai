## Текущий вывод

Основная функциональность локального прототипа реализована. Перед сдачей стоит провести короткую приёмку содержания и обновить опубликованный код. Оснований считать решение проверенным для регулярного наполнения каталога пока нет; для тестового достаточно показать пригодные черновики, понятные ограничения и воспроизводимый запуск. Полноценная CMS, БД и деплой исходным ТЗ не требуются.

До живой приёмки прошли 42 API-теста и 5 браузерных сценариев. После исправлений — 46 и 7 соответственно. API-тесты подставляют ответы провайдера; браузерные сценарии перехватывают запросы. Смысл новых ответов оценён отдельно в отчёте.

## Что уже видно при чтении результатов

- `examples/dm02.result.md`: основные известные параметры использованы, назначение соответствует входу. Заголовок — 38, описание — 827 символов. Для черновика это приемлемый результат ручного просмотра; устойчивость по одному ответу не установлена.
- `examples/training.result.md`: пропуски обозначены, но описание на 1196 символов перегружено повторными оговорками. В commercial-блоке «подходит для учебных задач» выводится из того, что сам набор учебный. Это слабое основание для утверждения о применимости прибора. Этот результат требует редакторской правки.
- Две искусственные подмены commercial-блока DM 02 приняты `check_draft` без ошибок: добавление корпуса из нержавеющей стали и «Диаметр корпуса — 1,5 мм» при исходных 100 мм. Модель эти подмены не генерировала: это проверка пределов валидатора. Совпадение токенов не доказывает правильную привязку свойства и значения.

Последние два пункта — причины для отдельной проверки содержания, а не доказательство, что любая новая генерация будет ошибочной. Текущий промпт уже требует избегать этих ошибок; менять его до получения новых наблюдений необязательно.

## Как провести проверку

1. Запустить приложение обычной командой из README. Открыть `http://127.0.0.1:8000`.
2. Открыть очередной файл из `evaluation/inputs/`, скопировать его содержимое во вкладку JSON и нажать «Создать карточку». Служебный `evaluation/cases.json` в форму не вставлять.
3. Сохранить JSON и Markdown результата **каждой попытки**, включая неудачную. Для локальных материалов использовать `artifacts/acceptance/<дата-и-время>/`, эта папка исключена из Git. Записать ID случая, номер повтора, дату, модель, время ожидания, ошибку или итоговый статус. Токены и число попыток брать из `metadata` ответа `/api/generate` в панели Network браузера; скачиваемый JSON содержит только карточку.
4. Сверить результат с исходником и ожиданиями из `evaluation/cases.json`. Повторные прогоны не заменять одним выбранным удачным ответом. Неудачу нельзя скрыть повторной генерацией.
5. Для 01 и 02 сделать по два независимых запуска. Остальные — по одному. Это 9 новых генераций; с учётом одной разрешённой коррекции каждая может сделать до двух API-запросов. 08 не должен обращаться к модели. Это небольшой приёмочный набор, не статистическая оценка надёжности.

Живая генерация расходует API. Эта инструкция сама запросы не выполняет. Существующий `docs.verify_live` работает только с двумя старыми примерами, перезаписывает их и имеет собственный общий лимит 12 запросов; новый набор он не запускает. Не удалять его журнал ради повторов.

## Критерии приёмки

Обязательные условия для каждой готовой карточки:

- Все технические утверждения можно связать с конкретным местом исходника. Проверять связку «свойство — значение — условие», а не только наличие числа.
- Нет новых материалов, сред, классов защиты, совместимости, условий эксплуатации, гарантии, наличия или преимуществ без подтверждения.
- Пропуски обозначены; уже известное не предлагается узнать заново. Противоречия явно раскрыты.
- Выполнены ограничения ТЗ по длине и составу карточки. Экспорты совпадают с показанным результатом.

Любая выдуманная техническая характеристика — FAIL независимо от красоты текста. Отказ или явная остановка на 05/06 может быть безопасным поведением, но записывается как SAFE_STOP, а не как успешно подготовленная карточка. Для обычных входов 01–04 и 07 одной ошибки генерации недостаточно для положительной приёмки.

Для полезности редактору отдельно поставить 0–2 по каждому признаку:

| Признак | Что означает 2 балла |
| --- | --- |
| Назначение и важные параметры | Читатель быстро понимает, что это за прибор и какие сведения о нём известны |
| Читаемость | Связный русский текст без повторов и искусственного растягивания |
| Поисковые запросы | Естественные релевантные формулировки без выдуманных свойств |
| Commercial-блок | Объясняет подтверждённую задачу подбора, не обещает неподтверждённую пригодность |
| Объём редакторской работы | Достаточно небольших правок; не нужно переписывать карточку заново |

Предлагаемый внутренний порог: не менее 8/10, ни одного нуля и соблюдены все обязательные условия. Это критерий нашей приёмки, в исходном ТЗ числового порога нет. Для 04 отдельно оценить, действительно ли стоит выпускать длинную карточку при почти пустом входе.

Проверка применимости в работе: контент-менеджер получает вход и результат, сверяет факты, редактирует текст и переносит его в каталог. Записать время ожидания и время правок отдельно, количество содержательных исправлений и нужен ли полный переписанный текст. Если сравнивать с ручным написанием, измерить его на сопоставимом входе; не объявлять экономию без такого сравнения. Оценка только автором и AI остаётся предварительной, до проверки реальным редактором.

## Когда сдавать

Для тестового достаточно: нормальные входы проходят обязательные критерии и ручной просмотр, сложные входы не приводят к ложным уверенным утверждениям, сценарий запуска воспроизводится, актуальная версия доступна в Git, происхождение второго примера раскрыто. Результаты прогонов и ограничения кратко приложить к сдаче. Раздувать прототип до промышленной системы для этого не нужно.

Второй предоставленный товар остаётся внешним пробелом исходных материалов: [вопрос работодателю уже подготовлен](employer-question.md). Можно сдать MVP с явным пояснением замены, но это не подтверждает буквальное выполнение пункта о двух предоставленных товарах.
