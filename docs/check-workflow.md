# Обязательная техническая проверка

Из корня проекта:

```bash
uv run --frozen python scripts/check.py
```

Нужны Python 3.11+ и uv. Первая проверка скачает Chromium; Linux также требует системные библиотеки браузера. На чистом Ubuntu их можно установить командой `uv run playwright install --with-deps chromium`. GitHub Actions делает это автоматически. Проверенный CI использует Python 3.12.

Команда собирает отдельную временную копию продуктовых исходников, ставит зависимости строго из uv.lock в новое окружение и последовательно запускает:

1. Тесты API, обогащения и обработки данных, включая пустой источник, краткую справку и проверки конкретных неподтверждённых утверждений.
2. Изолированные браузерные проверки: ввод и экспорты, копирование блока, восстановление после перезагрузки, нехватка данных и клавиатурные вкладки на узком экране.
3. Проверки с настоящими HTTP-маршрутами и процессами uvicorn: запуск без ключа, запрос дополнений без API, первый клик, реальный пример и скачивание, ошибка ключа, сломанный JSON, создание карточки и восстановление после ошибки провайдера. Среди них — отрицательная проверка, в которой не запускающийся сервер обязан дать ошибку готовности.

При любом неуспехе команда возвращает ненулевой код. В `artifacts/check/<время>/` остаются report.md, report.json, журналы, pytest.xml, архив проверенного исходного снимка, его хеши, скриншоты и трассы браузера. Временные серверы используют свободные порты; приложение пользователя на 8000 не перезапускается. При таймауте на Linux завершается вся группа процессов проверочного этапа.

Для проверки самого механизма обнаружения прежнего бага:

```bash
uv run --frozen python scripts/check.py --prove-regressions
```

После обычного успешного прогона команда временно возвращает в изолированной копии невыбранный пример. Проверка первого клика обязана упасть именно с ошибкой утверждения. Это ожидаемый отказ, явно отмеченный в отчёте; рабочие исходники не меняются. При изменении устройства выбора примера этот диагностический приём может потребовать обновления.

## Где проходит граница

Весь обычный прогон бесплатен относительно API: реальные ключи не передаются в дочернее окружение, .env.local не входит в снимок. Один настоящий сервер запускается без ключа. Другой использует ту же production app и маршруты, но заменяет только HTTP transport внешней LLM фиксированным ответом из tests/fixtures/provider-draft.json и синтетической документацией. Поиск, скачивание источника и проверка цитат проходят реальный код, внешние HTTP-ответы подменены. DNS для единственного домена фикстуры заменён только в тестовом процессе. Актуальные количества сценариев приводятся в отчёте прогона. Внутренние HTTP-запросы браузера в этом прогоне не перехватываются.

PASS означает прохождение перечисленных технических сценариев на конкретном снимке. **Смысловая оценка новых ответов LLM — NOT_RUN.** Её выполняют отдельно по плану приёмки, особенно после изменения промпта, модели или правил проверки. Эта команда также не подтверждает непрерывную доступность запущенного пользователем сервиса.

## Автоматический запуск

`.github/workflows/check.yml` выполняет ту же команду при push и pull_request и публикует проверку `quality`. Даже при ошибке сохраняются доступные артефакты. Workflow не использует API-секреты.

Для запрета непроверенных изменений ветка main должна требовать успешный статус `quality` именно от GitHub Actions. Сам файл workflow обеспечивает запуск, а требование успешного статуса настраивается отдельно в правилах ветки. Готовность конкретной версии подтверждается завершённым прогоном на её commit SHA, а не наличием этого файла.
